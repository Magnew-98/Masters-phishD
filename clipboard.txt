On the RAG question: what you are describing makes sense, but I would be precise in how you name it. This is not really “few-shot training” unless you are updating model weights. It is better described as few-shot prompting or retrieval-augmented few-shot prompting / in-context learning.

I would suggest structuring the experiments like this:

Zero-shot baseline
Give the model only the classification instruction and the email.
Fixed few-shot baseline
Give the model a small, fixed, balanced set of examples — for example, one phishing and one legitimate email, or a few of each.
RAG / retrieval-augmented few-shot run Use the training set as the retrieval pool and retrieve the most semantically similar labelled examples for each email being classified. This is the more dynamic version and is probably the most defensible use of RAG in your case.
I would not call the “one phishing + one legitimate” version RAG unless those examples are being retrieved dynamically per test email. If the same two examples are shown every time, it is simply a few-shot prompt, which is still useful as a baseline.

For the RAG setup, I think the larger training-data retrieval pool is the right direction. Just make sure that:

retrieval only uses the training split, not the test set;
near duplicates are removed or filtered carefully;
you report exactly how many examples are retrieved and whether they are balanced by class;
you keep the prompt, model, temperature, embedding model, and data split consistent across runs.
A good implementation would be something like: for each test email, retrieve the top k similar labelled examples from the training set, ideally with some class balance, then ask the LLM to classify the target email as phishing or legitimate. You can experiment with different k values, but keep this as an ablation study (i.e., something you do to validate the choice of k) rather than changing too many things at once.
